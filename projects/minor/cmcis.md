## 프로젝트 배경

CMCIS( Cardiology Monitoring and Central Information System )는 국책과제로 진행된 의료장비 통합 프로젝트다. 여러 제조사의 심장학(Cardiology) 관련 의료장비(심전도, 초음파, 혈압 모니터 등)에서 생성된 데이터를 하나의 시스템에서 통합 관리하고, 표준화된 인터페이스를 통해 다른 의료 정보 시스템과 연동하는 것이 목표였다.

의료 현장에서는 다양한 제조사의 장비가 혼용되어 사용되고 있고, 각 장비는 서로 다른 데이터 포맷과 통신 프로토콜을 사용한다. 이기종 장비 간 데이터를 통합하고, 병원 정보 시스템(EHR/EMR)과 연동하기 위한 표준화된 인터페이스가 필요했다.

주요 제약은 다음과 같았다.

- 여러 제조사 장비의 비표준 데이터 포맷을 표준 의료 데이터 형식으로 변환
- 실시간 생체 신호 데이터의 연속적 수집과 처리
- 의료 데이터의 무결성과 기밀성 유지 (개인 식별 정보 처리)
- HL7, DICOM 등 의료 정보 표준과의 호환성 확보

## 주요 기능

### 이기종 장비 데이터 수집

여러 제조사의 심장학 장비에서 실시간 생체 신호, 영상, 측정 데이터를 수집하는 기능.

- 구조: 장비 제조사별 데이터 수집 모듈을 플러그인 형태로 분리하여, 새 장비 추가 시 기존 코드 변경 없이 모듈만 추가 가능
- 처리: 실시간 연속 데이터(심전도 등)와 이벤트 기반 데이터(측정값, 알람 등)를 각각 다른 파이프라인으로 처리

### 의료 데이터 표준 변환 (DICOM / HL7)

각 장비의 비표준 데이터 포맷을 DICOM, HL7 등 의료 정보 표준 형식으로 변환.

- 기술 선택 이유: DICOM은 의료영상, HL7은 임상 정보 교환의 표준으로, 병원 정보 시스템과의 연동을 위해 두 표준 모두 지원 필요
- 구조: 장비별 데이터 형식 → 중간 표현(Intermediate Representation) → 표준 형식(DICOM/HL7)의 2단계 변환 구조. 중간 표현을 두어 표준 형식 추가나 변경 시 변환 로직 재사용 가능

### CMCIS 표준 인터페이스

국책과제에서 정의한 CMCIS 표준 규격에 따른 데이터 교환 인터페이스 구현.

- 구조: CMCIS 메시지 규격을 정의하고, DICOM/HL7 데이터를 CMCIS 규격으로 변환하는 매핑 레이어 구현
- 범위: Cardiology 관련 데이터 항목(심전도, 혈압, 초음파 측정값 등)에 대한 CMCIS 표준 정의 및 변환

## 설계 및 구현

### 표준 변환의 2단계 구조

장비 데이터 → 표준 형식 변환은 단순 매핑이 아니라 여러 단계의 처리가 필요했다. 각 장비의 데이터 단위, 측정 주기, 단위계가 모두 다르기 때문에, 직접 변환하면 N:M 변환 모듈이 필요해 유지보수가 어려워진다.

중간 표현(Intermediate Representation)을 정의하여 각 장비 데이터를 먼저 중간 표현으로 변환한 뒤, 다시 표준 형식으로 변환하는 2단계 구조를 선택했다.

- 장비별 모듈: 장비 데이터 → 중간 표현 (변환 로직 단순, 장비 추가 용이)
- 표준 변환 엔진: 중간 표현 → DICOM / HL7 / CMCIS (표준 추가 용이)

이 구조의 트레이드오프는 전체 변환 파이프라인의 레이턴시가 증가한다는 점이었다. 그러나 Cardiology 데이터는 초 단위 이하의 실시간성이 중요하지 않아, 유지보수성의 이점이 더 컸다.

### 플러그인 기반 장비 수집 모듈

새로운 제조사의 장비가 추가될 때마다 시스템 전체를 수정하지 않도록, 장비별 데이터 수집 모듈을 플러그인 형태로 분리했다. 공통 인터페이스(수집, 파싱, 전송)를 정의하고, 각 장비 제조사별로 이 인터페이스를 구현하는 구조다.

플러그인은 런타임에 동적 로드되며, 장비 탐색 및 자동 연결 기능을 통해 설정만으로 새 장비를 추가할 수 있도록 했다.

## 회고

의료장비 통합 프로젝트에서 기술적 난이도보다 어려웠던 점은 제조사별로 표준을 준수하는 방식이 조금씩 달라서, 같은 DICOM 표준이라도 장비에 따라 해석 차이가 존재한다는 것이었다. 이 차이를 중간 표현 레이어에서 흡수하는 설계가 실제로 효과적이었다.

프리랜서로 참여한 프로젝트였기 때문에, 장기적인 유지보수 관점보다는 기능 구현에 집중해야 하는 제약이 있었다. 플러그인 구조와 2단계 변환 구조는 이러한 상황에서도 확장성을 확보할 수 있는 방향이었다.

다시 만든다면, 초기 단계부터 다양한 제조사 장비의 실제 데이터 샘플을 확보하여 변환 규칙의 정합성을 더 체계적으로 검증했을 것이다. 표준 규격 문서만으로는 실제 장비 데이터에서 발생하는 예외 케이스를 모두 예측하기 어렵다는 경험을 얻었다.
